# Upstream relationship

This repository is a fork of [`dotnet/extensions`](https://github.com/dotnet/extensions) that publishes the WantsACracker migration packages. It is deliberately narrow: the only intended divergence from upstream is the mechanical substitution of Polly for the independently implemented `WantsACracker` APIs in the HTTP resilience integration, plus the accompanying package, namespace, and metadata renames.

## Branches

- `main` — upstream-tracking baseline. Branch-protected (no force pushes, deletions, or fork syncing). Never commit product changes here.
- `wants-a-cracker` — long-lived branch where all product work happens. Submodule pins in downstream repositories point at this branch.

## Baseline

- Upstream: `dotnet/extensions`
- Baseline commit: `cc597aa24bf108c38a6a59d09555765575d11cb3` — *Validate path segments in Azure storage result store and response cache (#7718)*
- Pinned on: 2026-08-26
- Polly versions at baseline (from `eng/Versions.props`): `9.0.18` (default), `10.0.10` (net10.0), `8.0.29` (net8.0) — superseded / corrected: these three values are the `MicrosoftExtensionsHttpPolly*Version` properties in `eng/Versions.props`, i.e. the versions of the `Microsoft.Extensions.Http.Polly` wrapper package, which neither `Microsoft.Extensions.Resilience` nor `Microsoft.Extensions.Http.Resilience` references; per the 2026-08-28 Polly package-graph finding, every Polly package in both projects actually resolves to `8.4.2` on all TFMs (pinned TFM-independently in `eng/packages/General.props`)

## Divergence rules

- Changes must be mechanical: package IDs, namespaces, and dependency references.
- Preserve upstream behaviour, structure, tests, metadata, and style unless a rename requires the change.
- No refactors, feature work, or unrelated cleanup in this branch.
- Every divergence carries a short rationale in its commit message.

2. **2026-08-30 — Swap the resilience libraries from Polly to the WantsACracker core package** (commit `3713f73be`; the mechanical `Polly` → `WantsACracker` using/type/namespace substitutions dominate the change set — the points below are the deliberate, non-mechanical divergences, each required for the substitution, with upstream behaviour, structure, and tests otherwise preserved):
    - `src/Libraries/Microsoft.Extensions.Http.Resilience/Internal/HttpKey.cs`: `HttpKey` is now `public` (upstream: `internal`). The delay-signed fork assembly cannot grant an effective `InternalsVisibleTo` to the *unsigned* `Castle DynamicProxyGenAssembly2` that Moq emits for `ResiliencePipelineProvider<HttpKey>` (the unsigned `WantsACracker` base type makes Castle emit an unsigned proxy, which can never match the keyed IVT), so the Moq-based pipeline-selection tests require the key type to be visible. The type is recorded in the `WantsACracker.Extensions.Http.Resilience.json` API baseline.
    - `src/Libraries/Microsoft.Extensions.Http.Resilience/Resilience/ResilienceHttpClientBuilderExtensions.Resilience.cs` (`CreatePipelineSelector`, null-key branch): builds the pipeline **eagerly** at handler creation (options validation fails fast with `OptionsValidationException`, as the reference implementation does) and then **fetches the pipeline per request** instead of caching the instance — the `WantsACracker` registry replaces the pipeline instance on dynamic reloads, so a cached instance would go stale (the reference implementation keeps one instance alive by swapping its internal component).
    - `HttpStandardResilienceOptionsCustomValidator` (`Resilience/Internal/Validators/`) and `HttpStandardHedgingResilienceOptionsCustomValidator` (`Hedging/Internals/Validators/`): the hand-written `IValidateOptions` validators now also mirror the range checks the `WantsACracker` `Add*` builder methods perform. The `WantsACracker` strategy options carry no data annotations, so the generated `[OptionsValidator]` code is empty; without these checks an invalid configuration would surface as an `ArgumentOutOfRangeException` at pipeline-build time instead of an `OptionsValidationException` at options-resolution time. The hedging delay is intentionally **not** range-checked: a negative delay (canonically `Timeout.InfiniteTimeSpan`) is a supported "wait indefinitely" configuration, matching the reference implementation.
    - `WantsACracker.Extensions.Resilience.csproj` / `WantsACracker.Extensions.Http.Resilience.csproj`: `CS8002` is suppressed in the two renamed src csprojs (and the two test csprojs) — the delay-signed assemblies reference the intentionally unsigned `WantsACracker` package, and .NET does not enforce strong-name verification. `DisableStrongNamer=true` is set in the two test csprojs so StrongNamer does not re-sign the unsigned reference and change its identity.
    - `NuGet.config` + `.gitignore` + `eng/local-packages/WantsACracker.0.1.0.nupkg`: a committed local package feed — the packed core package is committed, `NuGet.config` maps `WantsACracker` to the `eng/local-packages` source (via the `wants-a-cracker-local` `packageSource` entry and a matching `packageSourceMapping` pattern), and `.gitignore` re-includes `!eng/local-packages/*.nupkg` under its `*.nupkg` rule (the package version is pinned in `eng/packages/General.props`). **Local builds require the committed `NuGet.config` local feed** — a stale `wantsacracker/0.1.0` copy in the global NuGet cache can shadow the committed nupkg.
    - `WantsACracker.Extensions.Http.Resilience.csproj`: `SYSLIB1202` is suppressed — the `Http*StrategyOptions` types are empty subclasses of the `WantsACracker` strategy-options types, which validate their values in the `Add*` builder methods rather than via data annotations, so the data-validation source generator finds no validatable members on the subclasses and the warning is suppressed.

5. **2026-09-03 — The standard handler no longer retries non-replayable request bodies** (commit `b14cc8496`; non-mechanical — a safety-gate divergence, not a rename):
    - `src/Libraries/Microsoft.Extensions.Http.Resilience/Resilience/ResilienceHttpClientBuilderExtensions.StandardResilience.cs` (the `AddStandardResilienceHandler()` path): upstream composes the retry strategy unconditionally. The fork composes two standard pipelines — the ordinary one with the retry strategy and an identical one without it — and selects the pipeline **per request** via `HasReplayableContent`: content is replayable only when it is `null` or one of the built-in bufferable `HttpContent` types (`StringContent`, `ByteArrayContent`, `FormUrlEncodedContent`, `JsonContent`, `MultipartContent`); every other content shape (non-seekable `StreamContent`, custom `HttpContent` subclasses) is sent through the no-retry pipeline and is sent at most once.

    - Rationale: safety gate — the standard handler must never silently re-send a request body that cannot be replayed, and the replayability rule must match the behaviour users already get from the core's standalone standard handler.
